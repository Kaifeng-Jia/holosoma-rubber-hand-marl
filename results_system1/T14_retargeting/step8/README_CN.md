## 1. 新构造（`partner.py` 开头写全）

- **候选 S：**现有角色检查的候选对（第 7 步同样的构造和顺序；Push、Pull 用原来的 round-2 构造，目标是训练桌）。每对给出两个角色的区域映射 M0、M1（源物体坐标 → 加长后目标坐标）。
  - 在源物体坐标里，S_local = M0⁻¹·M1（角色 0 的区域 → 角色 1 的区域）；
  - 在世界里，S = O(0)·S_local·O(0)⁻¹，O(0) 取片段第一帧（物体静止）的物体位姿。
- **人：**角色 0 = 原示范；角色 1 = S·原示范（S 是镜像时左右关节、左右手、接触标签、手心目标一起交换；本轮只有 Pull 有镜像候选，见第 2 节）。
- **物体：**
  - 角色 0 对应 D0(t) = O(t)·O(0)⁻¹，角色 1 对应 D1(t) = S·D0(t)·S⁻¹；
  - 共享目标从 P(0) = O(0)·M0⁻¹ 出发，取 D0·P(0) 和 D1·P(0) 的中点：原点位置取均值，转动取 slerp 中点。
- **求解（第 1 节 CORE4D 共享场景第 3、4 步的做法，第 6 轮 C 设置）：**
  - 两台机器人围绕同一条共享轨迹分别求解。
  - 先验和初值：该角色的 Stage 1（角色 0 用源的；角色 1 用源的经 S 映射）按该角色锚点从自己的物体到共享物体的平均位移水平平移。
  - 锚点：源坐标里的手掌中位点经该角色的区域映射，投到目标碰撞盒上。
  - 交互网格：人一侧是该角色自己的物体，机器人一侧是源物体点经区域映射到共享目标上。
  - 其余同第 6 轮 C：先验 τ = 10 全 36 维 λ = 5；手心 / 手指 5 / 5；锚点 10；仿真几何；支撑脚锁定。
- **物体尺寸：**
  - 三个盒子：有向包围盒 × s（r = 1，同 Table、Chair 的共享物体）；位姿用 nominal（落地）轨迹。
  - Push、Pull：保持第 6 轮的物体，即训练桌、真实尺寸（Kevin 之前定的训练桌尺寸不变），位姿用 phys 轨迹。
- **源（盒子）：**角色 0 单独围绕自己的物体（盒子 × s）按同样设置求解一次（`role_solve.py --mode source`，含第 1 阶段）。它是角色检查的输入、V0 比较的基准、角色解的先验。Push、Pull 的源用第 6 轮 C 的单台求解。

## 6. 偏离和需要说明的

1. **候选集合按现在的源重算：**用的是现有检查的同一套构造和顺序，但输入是本轮的源机器人（盒子：r = 1 的源求解；Push、Pull：第 6 轮 C 的单台求解）。所以候选数和第 7 步、和当年的 Push（36 对）/ Pull（4 对）不同：Push 64 对、Pull 16 对；盒子 8–20 对。
2. **V0 只用了 Kevin 点名的四项**（重力方向、支撑脚漂移、非手部位穿透、两机间隙），阈值是冻结值。
   - V0 的其余项（FK 原点误差、手部区域距离、根部步长和加速度等）针对"刚性复制出来的机器人"，这里两台是分别求解的，没有用。
   - 支撑脚附加速度只报数。
3. **第 4 节的穿透验收没有用：**它要和"OmniRetarget 原样"比，这几条序列没有那个对照。接触验收只用了接触保持率 ≥ 0.99。
4. **CoCarry 的"物体在动"条件用的是共享轨迹的速度**（按人的尺度），因为机器人搬的是共享物体。
5. **主运动规则是这样落地的：**
   - b：共享目标原点离第 0 帧的最大水平距离 ≥ 0.5 m；
   - c：目标最低角离地 > 10 cm 的最长连续段 ≥ 15 帧。
   - 两条都按人的尺度（÷ s）。
6. **求解前先过门槛：**重力方向或主运动不过的候选直接判不过，没有求解；这些候选的门槛数字都在 `candidates.csv`。
7. **镜像的 S（只有 Pull 的候选里有）：**
   - 副本的人交换左右关节、左右手、接触标签和手心目标；
   - 副本自己的物体坐标系取 S·O·F，F = 桌子局部 XY 平面的镜像，这样坐标系是右手系。
   - 本轮 Pull 过了门槛的两个候选（c00、c05）都是镜像，走的就是这条路径。
8. **a：**每档两台重新求解，再按精确碰撞距离判断相交，从 1.0 往下每 0.05 一档，不低于 0.55。
9. **盒子：**第 7 步的有向包围盒 × s（r = 1），位姿用落地后的 nominal 轨迹。
10. **不适用的序列也出了并排图，只作示意：**取已求解候选里失败项最少的一个，图上写明"不适用，仅示意"。没有用它做参考。
11. **suitcase c 的候选 c00 角色 0 第一次求解崩了：**PyTorch 导入时的内部时钟断言（`getCount is non-monotonic`，SIGABRT）。主驱动结束后单独重跑了这个求解，并重做了 suitcase c 的评测和判定，日志 `records/driver_rerun_suitcasec.json`。崩掉的那次的输出移到了 `_to_delete/t14_step8/`。
12. **只在 1.0 倍上判定适用与否；**适用序列的其他档只报数，各档的判定结果也在 `levels.csv`。
