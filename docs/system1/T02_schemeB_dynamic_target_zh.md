# T02：方案 B，动态目标 + SONIC（2026-11-10 第二版）

**开始条件：** T04 中 D 的直接评测完成后，用本机 GPU 执行。第一版作废，以本版为准。

## 思路

方案 A 几乎全部失败。失败时机器人很少摔倒，主要是物体被落在参考后面；12 段参考里，机器人有 59/66 秒落后于参考。

B 用 SONIC 官方的交互接口，按规则闭环修正目标，不训练：
- **下半身：** 用运动学规划器（planner）生成，路点取参考骨盆路线。机器人偏离路线时，规划器会把它拉回来，这是位置反馈。
- **上半身：** 用 teleop 编码器的三点目标（左右手腕和躯干），可以再按物体的实际位姿修正手的目标，并往物体内侧偏一点。这是物体反馈。

这是别人用上层系统驱动 SONIC 时的标准做法（VR_3PT 模式），也是 SONIC 在本对比里最有利的用法。

## 适用任务

- Push、Pull、Chair、Bin、Table 五个任务。
- Kick 不适用：它的交互靠踢腿，而规划器只生成移动类的下半身动作，会把踢腿去掉。这一点在结果表里写明。

## 规则（每台机器人）

1. **规划器调用：**
   - 调用频率、上下文帧的来源、30 Hz 到 50 Hz 的重采样方式，一律按官方部署代码的实现，并在 README 里写明具体做法和代码出处。
   - batch 固定为 1，逐环境、逐机器人循环调用，CPU 推理即可。
2. **规划器的目标：**
   - `has_specific_target = 1`；
   - 4 个路点取参考骨盆在当前时刻之后的水平位置和朝向，时间间隔按规划器的预测长度均匀分布，具体取值写进预登记文件；
   - 目标速度取参考骨盆当前的水平速度；
   - 高度取参考骨盆当前高度；
   - mode 按官方文档选移动模式，写明选了哪个。
3. **teleop 编码器：**
   - 下半身未来帧取规划器的输出；
   - 三点目标取参考在当前时刻的左右手腕和躯干，按 SONIC 训练时的口径，表达在参考锚点坐标系里；
   - `motion_anchor_ori_b` 按训练时的口径计算。
4. **物体反馈（只作用于两个手腕目标）：**
   - 设参考物体位姿为 `T_obj_ref(t)`，实际物体位姿为 `T_obj_act(t)`。手腕目标改为 `T_obj_act · T_obj_ref⁻¹ · p_wrist_ref(t)`，再沿接触法向往物体内侧偏 δ。
   - 法向用 T02 第一版的离线预计算方法求，只在参考接触帧（手到物体表面 < 3 cm）施加。
5. **反馈只能修改上述目标，** 不改 SONIC、PD、机器人或物体。

## 变体（事先定，全部报告）

| 变体 | 下半身 | 手腕目标 | δ |
|---|---|---|---|
| B0 | 规划器，跟参考路线 | 参考原值 | — |
| B1-0 | 同上 | 按物体实际位姿修正 | 0 |
| B1-2 | 同上 | 同上 | 2 cm |
| B1-4 | 同上 | 同上 | 4 cm |

- **B0 和 A 的区别：** 一是换了接口，二是加了位置反馈。
- **B1 和 B0 的区别：** 加了物体反馈和压紧量。

## 开跑前的检查（门槛）

- **规划器单独验证：** 单机器人、无物体，用规划器加 teleop 编码器跟 SONIC 自带的示例走路路线（路点取该示例的骨盆路线）。不摔倒，且末帧骨盆水平误差 ≤ 30 cm，才算接通。不通过就停下回报。
- **坐标口径：** 三点目标的坐标口径和训练时一致。用 SONIC 自己环境导出的一帧数据核对，最大差 < 1e-5。
- **记录：** 每个回合记录规划器调用次数和总耗时。

## 评测

- **主设置：** 五个任务 × 四个变体 × ±2、±8 两档，各 50 个状态，另加 nominal 一个回合。协议与方案 A 相同（GPU PhysX、TF32 关闭、同一组初始状态文件、同一终止条件和指标）。
- **与 D 比较：** 按 README 预登记的口径做 McNemar 检验。
- **质量扫描：** 用 B0 和 B1-2 两个变体（事先定），跑 T04 中 Pull、Table、Bin 的全部质量档。
- **漂移：** 按 T01b 补充项的同一套漂移指标，报告 B 在完整任务中的骨盆漂移。
- **视频：** 每个任务、每个变体各一段 nominal 视频，不挑回合。
