# T03：方案 C，MARL + SONIC（2026-11-09）

**开始条件：** T01 验证 a 通过。可以和方案 A、B 的评测并行。

## 设计

C 和 D 只差一处：动作是直接作为关节目标（D），还是先经过 SONIC 再执行（C）。其余一律相同。

- **动作：** 每台机器人输出 29 维修正量 Δq，加到当前参考帧的关节角上，再交给 SONIC。
  - 动作缩放与 D 相同。
  - 输出层权重和偏置初始化为 0，所以第 0 次迭代时 C 和方案 A 完全一样。
  - SONIC 编码器要看的未来窗口，加同一个 Δq，记录做法。
- **SONIC：** 冻结，只做推理，不计算梯度。2,048 个环境 × 2 台机器人批量推理。
- **观测、critic、团队奖励、终止条件、MAPPO 超参数：** 与 V3 中 Table Pulling 的"从零训练"那组 run（V3-25–27）完全相同，包括并行环境数、每次迭代步数、学习率、clip、γ、λ。
- **初始化：** actor 从零开始。原因是单人先验的动作含义不同，不能直接用。
  - 因此 C 的对照组有两个：D 从零训练（V3-25–27），D 用先验初始化（论文主结果）。
- **迭代预算：** 与对照组 V3-25–27 的总迭代数相同，分段方式也相同。

## 任务与种子

- **任务：** Table Pulling（20 kg）、Table Transport（5 kg）。
- **Table Transport 的对照：** 论文主结果本来就是从零训练，直接作为对照，配置同样逐项对齐。
- **种子：** 先跑 721。
  - 两个任务的 721 都跑通后，再补 722、723。补种子是事先定好的，不看结果决定。
- **剔除规则（事先定）：** 只有 NaN/Inf，或者进程中断且无法从 checkpoint 续训，才算无效。无效的用同一个种子重跑一次，仍无效就换下一个种子号，并写明原因。

## 每次开训前

- 跑 smoke test：10 次迭代不报错；第 0 次迭代的 rollout 与方案 A 同一初始状态下的轨迹一致。
- 对 run_config 做逐字段 diff，对照 V3-25–27（Table Transport 对照论文主结果）。只允许与动作经过 SONIC 相关的字段、种子、目录、时间戳不同；diff 随交付提交。

## 评测与交付

- **评测：** 最终 checkpoint，不挑选；协议与方案 A 相同。
- **训练曲线：** 每个 run 的 mean_step_reward 等字段，口径与 V3 的 `curves/pull_training_scalars.csv` 相同。
- **训练成本（事先定的口径）：** 达到 D（先验初始化）最终 mean_step_reward 的 50%、80%、90% 所需的迭代数和环境步数；没达到的写"未达到"。另报每次迭代的平均秒数，注明 GPU 型号。
